1 ЗАВДАННЯ


Розгорнути програмну систему SmokeGuard на production середовищі та продемонструвати її роботу. Система включає серверну частину на базі NestJS, MQTT брокер EMQX для обробки IoT телеметрії від датчиків диму, базу даних PostgreSQL для зберігання подій та показань сенсорів, та IoT клієнти на мікроконтролерах ESP32 з датчиками MQ-2 для виявлення задимлення та DHT11 для виміру температури та вологості.

2 ОПИС ВИКОНАНОЇ РОБОТИ
2.1. Інфраструктура розгортання
Система розгорнута на VPS сервері з операційною системою Ubuntu Server, що забезпечує стабільне середовище для production використання. Для організації інфраструктури використано контейнеризацію Docker, що дозволяє ізолювати компоненти системи, спростити процес deployment та забезпечити узгодженість між development та production середовищами.
        Всі сервіси об’єднані у власну Docker мережу smokeguard-network для ізольованої комунікації. Кожен сервіс має налаштований healthcheck для автоматичного моніторингу стану: PostgreSQL перевіряється через команду pg_isready, EMQX через emqx ping. Backend контейнер запускається тільки після успішних healthcheck усіх залежних сервісів, що забезпечує коректну ініціалізацію системи.
Для production розгортання використовується домен smoke-guard.pp.ua, зареєстрований через український реєстратор NIC.UA. Налаштовано SSL сертифікати від Let’s Encrypt для забезпечення шифрованого HTTPS з’єднання. Swagger документація автоматично генерується та доступна за адресою https://api.smoke-guard.pp.ua/api/docs з повною специфікацією всіх endpoints.


2.2. Автоматизація розгортання
Процес розгортання повністю автоматизовано через GitHub Actions CI/CD pipeline. При кожному push коду до гілки main автоматично запускається двоетапний процес: спочатку виконується збірка оптимізованого Docker образу та його публікація в GitHub Container Registry, а потім здійснюється deployment на VPS сервер через SSH підключення.


deploy:
  runs-on: ubuntu-latest
  needs: build-and-push
  steps:
    - name: Deploy to VPS
      uses: appleboy/ssh-action@master
      with:
        host: ${{ secrets.VPS_HOST }}
        username: ${{ secrets.VPS_USER }}
        key: ${{ secrets.VPS_SSH_KEY }}
        script: |
          cd /opt/smokeguard
          docker compose -f docker-compose.prod.yml pull
          docker compose -f docker-compose.prod.yml up -d
          docker image prune -f


Deployment скрипт підключається до VPS, завантажує нову версію backend образу через команду pull, перезапускає оновлені контейнери в фоновому режимі та очищає старі невикористовувані образи. Такий підхід забезпечує мінімальний downtime при оновленні системи та дозволяє швидко відкотитися до попередньої версії у разі потреби.
2.3. Docker Compose конфігурація
Всі компоненти системи описані в декларативному форматі Docker Compose. Конфігурація включає визначення сервісів PostgreSQL з персистентним volume для збереження даних, EMQX з експозицією портів для MQTT протоколу, та backend сервіс, який залежить від готовності інших компонентів. Кожен сервіс має налаштований healthcheck: PostgreSQL перевіряється через pg_isready, а EMQX через команду ping.


backend:
    image: ghcr.io/${GITHUB_REPOSITORY}:latest
    depends_on:
      postgres:
        condition: service_healthy
      mqtt:
        condition: service_healthy
    ports:
      - '3000:3000'
    command: sh -c "npm run migration:run && node dist/main.js"




Backend контейнер стартує лише після того, як усі залежні сервіси успішно пройдуть healthcheck і будуть готові до приймання з’єднань. Під час запуску автоматично виконуються міграції бази даних за допомогою TypeORM, що забезпечує відповідність схеми бази поточній версії коду. Застосування іменованих volumes дозволяє зберігати всі дані навіть після перезапуску контейнерів.


2.4. Налаштування IoT клієнтів
ESP32 датчики диму налаштовуються через вбудований веб-портал конфігурації, реалізований на стандартних бібліотеках WiFi та WebServer, що дозволяє виконувати первинне та повторне налаштування без перепрошивки. При першому запуску пристрій автоматично переходить у режим Access Point, створює власну WiFi-мережу та надає доступ до веб-інтерфейсу за адресою 192.168.4.1. Через нього користувач задає параметри WiFi, MQTT брокера та ідентифікаційні дані датчика, отримані після його реєстрації у backend системі через REST API. Усі налаштування зберігаються в енергонезалежній пам’яті ESP32, після чого пристрій перезавантажується та підключається до заданої інфраструктури.


Після налаштування датчик автентифікується в MQTT брокері EMQX через backend, що забезпечує централізований контроль доступу IoT пристроїв. У робочому режимі ESP32 періодично публікує телеметрію та heartbeat-повідомлення, а також підписується на MQTT-команди керування сигналізацією. Backend у реальному часі обробляє отримані дані, зберігає показання, формує події при виявленні диму та ініціює відповідні реакції системи.

ВИСНОВКИ
У ході виконання лабораторної роботи було реалізовано та розгорнуто повнофункціональну IoT систему виявлення задимлення SmokeGuard на production VPS сервері з використанням контейнеризації Docker. Система має власний домен, захищений SSL сертифікатами, та використовує автоматизований CI/CD процес на базі GitHub Actions, що забезпечує безпечне та стабільне оновлення сервісів без ручного втручання.
Розроблене рішення демонструє стабільну роботу IoT інфраструктури, включаючи зручне налаштування ESP32 клієнтів через WiFi веб-портал, обробку телеметрії від датчиків у реальному часі та автоматичне відновлення з’єднання при збоях. Архітектура системи підтримує масштабування за рахунок підключення нових датчиків без змін у серверній логіці та забезпечує надійне збереження даних.
